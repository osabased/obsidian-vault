# Agent taste vault

The user's taste, kept as a small wiki so Claude Code can apply it. The agent proposes rules in session when the user corrects it or a failure or dated source shows what works, and the hooks in `tools/hooks/` deliver the rules the user confirms back to the agent. The user reads and edits the notes in Obsidian.

## Layout

- `raw/` holds sources and is append-only.
  - `raw/inbox/<date>.jsonl`: rules the agent proposed in session (`source: agent`, `a-` ids), written by `tools/propose.mjs`. Older rows, with `c-` and `p-` ids, are preferences captured from sessions before proposals existed.
  - `raw/picks/<date>.jsonl`: questions the agent asked in domain sessions and the user's answers, word for word, with `q-` ids, captured alongside those older rows.
  - `raw/decisions.jsonl`: what became of each inbox and pick row, by id. `tools/propose.mjs` records the note it wrote for each proposal; older rows are review decisions.
  - `raw/judgments/`: the user's picks between design options, verbatim and dated ("B over A because…"), usually with the user's reason. You may add a new file here when the user makes a pick.
  - `raw/refs/`: references the user collects. You may add new files here.
- `wiki/<domain>/<slug>.md`: one rule per note. Domains and their project folders are in `taste.config.json`. Rules in `wiki/global/` apply in every project.
- `confirmed.json`: the ledger of confirmed rules. Only the hooks write it, when the user confirms or retires a rule in chat.
- `active.md` and `index.md`: generated by `node tools/build.mjs`.
- `log.md`: confirmations, retirements and drops, newest last. Older entries also record review decisions.
- `tools/`: the hooks and scripts. Read `tools/CODING_STANDARDS.md` before changing them.

## How rules reach the agent

A rule takes effect only once the user confirms it. Then:

- `always: true` rules load at the start of every session in the domain's projects.
- Rules with `applies_to` refuse the first matching edit to each file in a session and show the rule. The retry goes through.
- Rules with `keywords` are shown when a prompt mentions one of them.

The hooks deliver the wording recorded when the user confirmed, not the live note. If a confirmed note changes, the old wording stays in force until the user confirms again.

## Rule notes

```markdown
---
type: rule
domain: roblox-ui
status: provisional
kind: taste
basis: stated
topic: code
always: false
applies_to:
  - 'src/client/UI/**/*.luau'
triggers: []
keywords:
  - strict
replaces: []
created: 2026-10-19
updated: 2026-10-19
---

**Do:** Start every UI script with `--!strict`.
**Not:** Leave scripts in nonstrict mode.
**Because:** Type errors should show up while editing, not in play tests.

## Examples

## Evidence
- 2026-10-19 · stated · session 1a2b3c4d · "I want the agent to always write scripts in !strict" (a-1a2b3c4d)
```

- `status`: `provisional`, `confirmed` or `outdated`. Only the user's confirm (a bare `confirm` or `confirm: <key>`) makes a rule confirmed, and the hook sets the field.
- `kind`: `taste` (the default) or `knowledge`, a fact about an API, version or tool that training gets wrong or doesn't know. Knowledge rules reach the agent only on matching edits, so they need `applies_to` and take no `keywords` or `always`.
- `basis`: `stated` when the user said it, `inferred` when you generalized it from their corrections. Knowledge rules use `stated`, `failure` (something worked only after a failure) or `source` (a dated source shows it).
- `as_of`: knowledge rules only, the day the fact was last checked, as YYYY-MM-DD: the source's date, or the day it was proposed. Delivery shows it, and lint warns once it is more than 180 days old (`knowledge.staleAfterDays` in `taste.config.json`). Taste rules never expire.
- `topic`: one of the domain's topics in `taste.config.json`.
- `always`: only for short rules that matter in nearly every session.
- `applies_to`: globs relative to the project root. `**` crosses folders, `*` doesn't, `{a,b}` picks one. Matching ignores case and worktree folders.
- `triggers`: optional regexes tested against the new text of an edit. When present, the rule applies only if one matches.
- `keywords`: optional words or phrases that bring the rule up from a prompt.
- `replaces`: keys of rules this one supersedes, like `roblox-ui/old-slug`, from its own domain; a global rule may replace any. Confirming this note retires them.
- Single-quote globs and regexes so Obsidian reads them as text.
- `**Do:**` and `**Not:**` are required, one line each. Pair every "never X" with an "instead Y". `**Because:**` gives the user's reason; leave it empty rather than invent one. Keep the three lines under 300 characters together, counting the "As of" date a knowledge rule is delivered with.
- `## Evidence` has one line per source: date, kind (`stated` or `correction`, or `choice` in older notes), the first 8 characters of the session id, the user's exact words, and the proposal id. A `failure` line gives the file, the error as a tool printed it and `fixed by:` the fix; a `source` line gives the URL or `raw/refs/` file, `dated` its date, `summary` when the quote comes from a WebFetch summary rather than the page, and its exact words.
- Link notes with `[[wiki/<domain>/<slug>|<slug>]]`.

## What belongs here

The vault holds one-line Do/Not rules. Procedures, how-tos and project facts belong in the project's guides, skills and auto memory. Don't propose what the project's CLAUDE.md or `.claude/rules/` already says.

## Operations

- **Propose**: in domain sessions the start hook tells you how to propose a rule with `tools/propose.mjs` when the user corrects you, or when a failure or a dated source shows a fact your training gets wrong. `node tools/propose.mjs --help` lists the fields. When the rule may repeat ones the user confirmed, it lists them and refuses once; you propose again with the key of the one it repeats in `replaces`, or `replaces: []`. It writes a provisional note, and you end your reply with the lines it prints. The user answers with a bare `confirm` or `drop`, which takes the proposal made since their last message, or later with `confirm: <key>` or `drop: <key>`. `drop:` marks a provisional note outdated so it isn't offered again; confirmed rules need `retire:`. The hooks take these commands only in a session where the user has typed a message.
- **Review**: the user runs `/taste-review` in this folder for a check-up: rules changed since they were confirmed, provisional rules waiting for a confirm or drop, repeats of confirmed rules, lint and hook errors.
- **Query**: when asked what the user prefers, read `index.md`, then the notes. Confirmed rules are the user's taste; provisional ones are candidates. Say which is which.
- **Lint**: `node tools/lint.mjs` checks notes, the ledger and the generated files. The pre-commit hook rebuilds the generated files and runs it.

## Evidence

- A stated preference or a correction from one session is enough for a provisional note.
- When evidence conflicts, show the user both sides and let them decide.
- A knowledge rule needs a failure that a command or a failed tool call printed in the session where it was fixed, or a source with its date: a URL fetched in that session, or a file in `raw/refs/` that the session didn't write. A subagent's tool calls count; its report doesn't. An error in a file a command only showed or on a browser page doesn't count, and neither do words the agent gave the tool.
- The user's own taste beats general best practice. Don't add rules they didn't express, unless the evidence is a recorded failure or a dated source, and the user confirms.

## Never

- Edit `confirmed.json`, `active.md`, `index.md`, or existing files in `raw/` or `.state/`.
- Write `status: confirmed`, or change the Do, Not, Because, `applies_to`, `triggers`, `keywords` or `always` of a confirmed note, or the `kind` or `as_of` of a confirmed knowledge rule. Write a new note with `replaces:` instead, and ask the user to confirm it.
- Confirm, retire or drop rules yourself, including through a shell command. If the user types `confirm:`, `retire:` or `drop:` and you see it as a normal message, the hooks aren't loaded in this session: tell them to start a new one. A bare `confirm` or `drop` reaches you when nothing was proposed since their last message: ask them for the key.

The hooks refuse most of these. They guard against mistakes, not deliberate workarounds.

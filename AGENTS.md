# Agent taste vault

The user's taste and knowledge, kept as a small wiki so an agent can apply and look them up. The agent writes rules in session when the user corrects it or a failure or dated source shows what works, and the hooks in `tools/adapters/<agent>/hooks/` deliver them back to the agent from then on. Pages hold knowledge in the agent's words, or in the user's on pages they write (`author: user`), and sessions read them through `index.md` or when a hook points to one. The user reads, edits and deletes the notes in Obsidian.

## Layout

- `raw/` holds sources and is append-only.
  - `raw/inbox/<date>-<session>.jsonl`: rules the agent proposed in session (`source: agent`, `a-` ids), written by the `propose` and `keep` tools (see Inbox rows in `reference/notes.md`), one file per session named by its short name: the first 8 characters of the session id, or the last 8 for an agent whose ids share their start, as the `propose` tool writes it in Evidence lines.
  - `raw/picks/<date>-<session>.jsonl`: the user's picks between options and their comments on one piece of work, word for word, with `q-` ids, written by the `pick` tool (see Picks in `reference/notes.md`), one file per session too. The sheet a pick was made from sits beside them as `<date>-<subject>.<ext>`.
  - `raw/refs/`: references the user collects, and the text of web pages `/ingest` saved, each starting with frontmatter that gives its `url` and the day it was `fetched`. A page a browser saved whole, `<name>.html` with the files it shows in `<name>_files/`, is one source, named by its `.html`, and so is a bundle (see Pages in `reference/notes.md`). You may add new files here. Lint also reads `etag`, `last_modified` and `sha256` (of the text below the frontmatter), or `repo`, `path` and `commit` for a file from a git repository, and warns on one in the wrong shape. `tools/refresh.mjs` writes `etag`, `last_modified` and `sha256`, and each new copy of a source that changed, `<stem>.<8 hex>.md` with `replaces` naming the copy before it, or `baseline: true` on the first copy of a source saved without a hash; leave all of them to it. To cite a file from a git repository, save it as `raw/refs/<name>.md` with `repo`, `path` and `commit` (the full hash) and the file's text at that commit below, and quote from that text.
- `derived/<sha256>.md`: the text extracted from a binary source in `raw/`, named by the binary's SHA-256. `node tools/extract.mjs <file>` writes it, through the first extractor in `tools/ext/extractors/` that `extractors` in `vault.config.json` lists for the file's extension (see Pages in `reference/notes.md`).
- `wiki/<domain>/<folder>/<slug>.md`: one rule per note, or a page (see Pages in `reference/notes.md`), in its domain's folder for its kind: `rules/`, or `topics/`, `concepts/`, `entities/`, `syntheses/` or `sources/`. A note's key is `<domain>/<slug>` whichever folder holds it, so a slug is used once in a domain: lint reports two notes with one as errors, and neither is delivered. A note in another folder is still read as its frontmatter says, and lint warns. Domains are in `vault.config.json`, with the sessions each reaches (see `reference/delivery.md`). Rules in `wiki/global/` reach every session.
- `reference/notes.md`: the formats of rule notes, pages and picks, field by field. Read it before you write or edit a note or page by hand, or to explain one of their fields.
- `reference/delivery.md`: how rules and pages reach each session, and what the session start and the status line say. Read it to explain why a rule or page did or didn't reach a session.
- `active.md`, `index.md` and `decisions.md`: generated by `node tools/build.mjs`, which each session start and each pick also run. `index.md` lists every page and rule by topic: the topic's pages first, by kind with the topic page leading, each with how many sources it draws on and its summary, then its rules. `decisions.md` lists the picks and comments by domain, project and subject, newest first, with their sheets.
- `log.md`: the notes the `propose` and `keep` tools wrote or added evidence to, the operations the `log` tool logged (a page changed on its own, an ingest, an answer filed back) and each `/lint` run's tally, newest last. Older entries record confirmations, retirements, drops and review decisions from before rules went live on writing.
- `.state/`: the hooks' and tools' bookkeeping, including which rules and pages each session was shown, the offers waiting for the user's agreement (`offers/`) and the record of each tool call that ties it to its session (`calls/`), `derived.json`, which refresh and build write, and `versions.json`, the versions read from each project's lockfile.
- `tools/`: the hooks and scripts. `tools/adapters/<agent>/` holds what is one agent's, its hooks included; the rest of `tools/` is the core and the scripts. The vault's tools, `propose`, `keep`, `proposals`, `domain`, `pick`, `log`, `search` and `status`, are scripts here that the plugin's MCP server runs for a session, each taking JSON (see Vault tools in `reference/delivery.md`); a test or a person can pipe the same JSON to a script. Read `tools/CODING_STANDARDS.md` and `reference/delivery.md` before changing them. Sessions run the hooks and the tools from `.live/tools/`, a copy of `tools/` at the last commit, which session start and the tool server make again when a commit changes `tools/`, and `.githooks/post-commit` after each commit, so a change to the tools reaches project sessions once it's committed; a session in this folder runs the working `tools/`.
- `.agents/skills/`: copies of `.claude/skills/` for agents that read skills there. Edit a skill in `.claude/skills/`; lint reports a copy that differs other than in line endings, and `node tools/lint.mjs --fix` writes it. Lint also reports a copy whose skill is gone, naming the folder to delete, which `--fix` leaves.

## What belongs here

- **Rules** are one-line Do/Not taste, and facts training gets wrong, that the hooks deliver. Propose a rule only for what the project's own agent instructions, such as CLAUDE.md, AGENTS.md or `.claude/rules/`, don't already say. A compiled taste-vault section in them is the vault's copy, not the project's own.
- **Pages** are knowledge: concepts, APIs, comparisons, what sources say, and research on any topic, including the background a rule's one line leaves out.
- **Procedures and how-tos**, steps an agent follows, belong in skills; a page may link one. **Project facts**, such as how one project is built or where its files live, belong in that project's CLAUDE.md, docs or auto memory.

## Operations

- **Propose**: in domain sessions the start hook tells you to propose a rule through the vault's `propose` tool when the user corrects you, or when a failure or a dated source shows a fact your training gets wrong. In this folder, a session proposes for any domain, as `/ingest` does; a session in a folder no domain reaches proposes to `global` only. The tool's schema lists the fields. Outside this folder, the `proposals` setting decides when you propose (see Set when rules are proposed). In `corrections` it writes the note, which applies from then on, and you end your reply with the lines it returns, so the user sees the rule and can edit or delete it. When the rule may repeat ones in the vault, or its words already back another note, it lists them, each marked shown or not shown in this session since its last compaction, and refuses once: propose again with `repeats` set to the rule it repeats, and the tool adds its Evidence line to that note, or propose again as it is if it says something new. Once it writes the note, it names the rules on the same topic whose `applies_to` covers files the new rule's does, so you check the two don't contradict.
- **Set when rules are proposed**: `proposals` in `vault.config.json` is `corrections`, `ask` (the default) or `off`, and a domain may set its own under `domains.<d>.proposals`, which its rules take; `global`'s take the top-level one. In `corrections`, you propose a rule as soon as the user corrects you. In `ask`, `propose` runs every check and then returns the rule as an offer with an id, writing nothing. In `off`, you propose only when the user asks you to keep a rule, with their words asking as `asked`, which only gates the offer and has no power to write. The user then agrees to the offer, and how depends on the agent. Where the client asks the user before it runs a tool, you call `keep` with the offer's id and lines, and the user allows or denies the call at that prompt: Allow once is their agreement, and a Deny ends that proposal. Where it doesn't, the offer ends with a short code, and once the user's next message holds it you call `keep`. `keep` checks that the lines are the offer's, runs the checks again, writes the note and records the consent in the inbox row. It covers adding evidence through `repeats` too. Without a transcript a session can't quote the user, and it gets no offer in `off` or where the user agrees by code. A session in this folder proposes as in `corrections` whatever the mode, since `/ingest` goes through each rule with the user. The start hook tells each session its mode. To change it, the user runs `/vault <mode> [domain]` or asks in words, and you call the `proposals` tool with `mode` and `domain`; the user agrees as to a rule, and it changes only that key and logs the change. Lint reports any other value as an error.
- **Limits of consent**: the check ties a call to its session through a record the hooks write in `.state/calls/`, so a raw shell write there can forge one, like any raw shell write. A shell run that drops the agent's session variable can name another session, and a vault-folder session's id writes as in `corrections`. A `propose` sent in parallel while that text's `keep` prompt is open reads as declined. `dontAsk` mode denies `keep`, and a non-interactive run can't approve it. A host that answers permission requests in code can approve a `keep` for the user. Whether a permission-request hook's `allow` skips the prompt is unverified. Where the client has no tool prompt, its own prompt plays no part in consent and its tool list is fixed for the connection; a hook failure there doesn't block the call, but the server refuses it anyway.
- **Re-propose a recorded answer**: a pick or comment that was never turned into a rule can back one from any later session: `basis: pick` with the row's id in `pick`. The row's words are the evidence, so nothing has to be typed again. A row backs one note; proposing it again is refused.
- **Record a pick**: in domain sessions the start hook tells you how to record each pick and comment with the vault's `pick` tool, and to call it with `show` before building or reviewing a piece that has picks.
- **Start a domain**: when a preference holds only for projects of a kind no domain covers, suggest a domain to the user: a name, a title, its topics, and a file that marks the kind, or this folder alone when no file does. Ask in your reply, since an option the user picks is your words, not theirs. Once they agree, call the vault's `domain` tool (its schema lists the fields). It returns an offer in every mode, this folder included, and the user agrees to it as to a rule. Start a domain only this way, and only once they agree.
- **Ingest**: the user runs `/ingest` in this folder with a source: a file, or a URL whose text it saves to `raw/refs/`. You go through it together; it becomes a source page, what they say about it becomes taste rules and the dated facts they keep knowledge rules, and every topic, concept and entity page it touches is updated. A source that fits no domain gets an offer of a new one, `vaultOnly: true` when it holds pages only. Before going through a source, `/ingest` extracts a binary's text and scans every source, a bundle's files each, for key- or token-shaped text, and stops on either until the user decides. An image no extractor reads isn't a stop: its text goes unscanned, the user is told, and it backs `basis: reading` only. `/ingest batch` takes in, without the user, every file `node tools/review.mjs sources` lists, leaves for the user each one either step stops on, and asks before adding any rule.
- **Query**: when asked what the user prefers or what the vault knows, or when a task touches a topic the session start names, read `index.md`, then the pages and notes on the topic. To find notes by their words rather than their topic, call the vault's `search` tool with the words; its schema lists the filters. Every rule in the vault is the user's taste; a rule with `basis: inferred` is your generalization of their corrections, and one with `basis: reading` is your reading of what they showed you, so say so when you lean on either.
- **File back**: when an answer drawn from the vault would help a later session, from any session, add it to the page it extends, or file it as a synthesis page and link that from the topic's page, then call the vault's `log` tool with `query` the question and `pages` every page you changed.
- **Lint**: the user runs `/lint` in this folder for a check of the whole wiki: lint findings, hook errors, rules corrected again in later sessions, rules no session was shown, contradictions, repeats, listed topics no rule has yet, stale pages, concepts with no page, claims a newer source overrides, gaps worth a web search, and files in `raw/refs/` no source page names yet. Its first step, `node tools/refresh.mjs`, checks each saved source against its URL or repo and saves a new copy of each one that changed, and offline reports the failed checks and goes on; a note citing an older copy is labelled `source changed on <date>` until it cites the new one. Refresh never runs on its own. The next step, `node tools/review.mjs status`, records the run, which quiets the session-start error line and reminder, and logs its lint tally in `log.md`. `node tools/lint.mjs` on its own checks the notes and the generated files, warns on a compiled section in a project of a `compile` domain that is missing, stale or edited by hand and names the `node tools/compile.mjs` command to run, and with `--fix` rewrites the link, footnote and source paths it gives the spelling of, outside the user's quoted words, writes the skill copies in `.agents/skills/` that are missing or differ, and rebuilds the generated files; the pre-commit hook rebuilds the generated files and runs it, runs the tests in `test/` when the commit changes `tools/`, `test/`, `hooks/`, `.githooks/` or `.claude-plugin/`, and refuses a commit that rewrites, renames or removes a file in `raw/` unless `VAULT_ALLOW_RAW_CHANGES=1` is set.

## Evidence

- A stated preference or a correction from one session is enough for a rule.
- Cite what backs each rule as it is: the user's words, the error a tool printed and its fix, a dated source and its words, or your own reading. Quote the user's or the source's exact words, marking words left out with …, and give anything else as your reading: the `propose` tool refuses a quote the user never typed in this session, one a text file under `raw/refs/` or a binary's derived text doesn't hold, one against a binary with no derived text, a source quote against an image, which backs `basis: reading` only, or one the user's page it cites doesn't hold, and lint warns on each such quote already in a note. Lint checks a quote whose transcript is gone against the `raw/inbox/` row that recorded it, and counts in one warning the quotes it can't check, those citing a URL or a gone session with no row; `node tools/review.mjs status` lists them.
- When evidence conflicts, show the user both sides with the one you recommend first, say what decided it, and let them decide. Between taste rules, prefer the stronger basis (`stated`, then `pick`, then `inferred`, then `reading`), then the one with more Evidence lines, then the newer evidence. Between knowledge rules, prefer the one that matches the project's version, then the newer `as_of`. A taste rule and a knowledge rule aren't ranked. For rules whose globs overlap, `node tools/review.mjs status` and the `propose` tool print this ranking; rank the others yourself. When the two rules' `applies_to` cover different files, keeping both may be the answer.
- The user's own taste beats general best practice. Write rules they expressed, ones a failure or a dated source backs, or your reading of what they showed you, labelled as yours.

## Never

- Change a file that already exists in `raw/`. Put new material in a new file under `raw/refs/`.
- Change the user's words: the quotes under `## Evidence` and `## You said`, and a page with `author: user` outside its `## Agent notes`. Add a line instead.
- Write outside the vault. The one exception is `node tools/compile.mjs`, which the user runs for a project whose domain lists an agent under `compile`; it writes only that project's `AGENTS.md`, inside its marked section. `node tools/agents.mjs <agent>` prints the hooks, and the tool server where the agent needs one, for the user to install or merge, and writes nothing.

The hooks refuse the first, the edits to a user's page the second forbids, and edits to `active.md`, `index.md`, `decisions.md`, `vault.local.json`, `derived/`, `.state/`, `.sources/` and `.live/`, and, from outside this folder, an edit that makes any note under `wiki/` a new rule, which only the `propose` and `keep` tools add. They guard against mistakes, not deliberate workarounds.

# Agent taste vault

The user's taste and knowledge, kept as a small wiki so an agent can apply and look them up. The agent writes rules in session when the user corrects it or a failure or dated source shows what works, and the hooks in `tools/adapters/<agent>/hooks/` deliver them back to the agent from then on. Pages hold knowledge in the agent's words, or in the user's on pages they write (`author: user`), and sessions read them through `index.md` or when a hook points to one. The user reads, edits and deletes the notes in Obsidian.

## Layout

- `raw/` holds sources and is append-only.
  - `raw/inbox/<date>-<session>.jsonl`: rules the agent proposed in session (`source: agent`, `a-` ids), written by `tools/propose.mjs`, one file per session named by its short name: the first 8 characters of the session id, or the last 8 for an agent whose ids share their start, as `propose.mjs` writes it in Evidence lines.
  - `raw/picks/<date>-<session>.jsonl`: the user's picks between options and their comments on one piece of work, word for word, with `q-` ids, written by `tools/pick.mjs` (see Picks), one file per session too. The sheet a pick was made from sits beside them as `<date>-<subject>.<ext>`.
  - `raw/refs/`: references the user collects, and the text of web pages `/ingest` saved, each starting with frontmatter that gives its `url` and the day it was `fetched`. A page a browser saved whole, `<name>.html` with the files it shows in `<name>_files/`, is one source, named by its `.html`, and so is a bundle (see Pages). You may add new files here. Lint also reads `etag`, `last_modified` and `sha256` (of the text below the frontmatter), or `repo`, `path` and `commit` for a file from a git repository, and warns on one in the wrong shape. `tools/refresh.mjs` writes `etag`, `last_modified` and `sha256`, and each new copy of a source that changed, `<stem>.<8 hex>.md` with `replaces` naming the copy before it, or `baseline: true` on the first copy of a source saved without a hash; leave all of them to it. To cite a file from a git repository, save it as `raw/refs/<name>.md` with `repo`, `path` and `commit` (the full hash) and the file's text at that commit below, and quote from that text.
- `derived/<sha256>.md`: the text extracted from a binary source in `raw/`, named by the binary's SHA-256. `node tools/extract.mjs <file>` writes it, through the first extractor in `tools/ext/extractors/` that `extractors` in `vault.config.json` lists for the file's extension (see Pages).
- `wiki/<domain>/<folder>/<slug>.md`: one rule per note, or a page (see Pages), in its domain's folder for its kind: `rules/`, or `topics/`, `concepts/`, `entities/`, `syntheses/` or `sources/`. A note's key is `<domain>/<slug>` whichever folder holds it, so a slug is used once in a domain: lint reports two notes with one as errors, and neither is delivered. A note in another folder is still read as its frontmatter says, and lint warns. Domains are in `vault.config.json`, with the sessions each reaches (see How rules and pages reach the agent). Rules in `wiki/global/` reach every session.
- `active.md`, `index.md` and `decisions.md`: generated by `node tools/build.mjs`, which each session start and each pick also run. `index.md` lists every page and rule by topic: the topic's pages first, by kind with the topic page leading, each with how many sources it draws on and its summary, then its rules. `decisions.md` lists the picks and comments by domain, project and subject, newest first, with their sheets.
- `log.md`: the notes `tools/propose.mjs` wrote or added evidence to, the operations `tools/log.mjs` logged (a page changed on its own, an ingest, an answer filed back) and each `/lint` run's tally, newest last. Older entries record confirmations, retirements, drops and review decisions from before rules went live on writing.
- `.state/`: the hooks' bookkeeping, including which rules and pages each session was shown, `derived.json`, which refresh and build write, and `versions.json`, the versions read from each project's lockfile.
- `tools/`: the hooks and scripts. `tools/adapters/<agent>/` holds what is one agent's, its hooks included; the rest of `tools/` is the core and the scripts. Read `tools/CODING_STANDARDS.md` before changing them. Sessions run the hooks from `.live/tools/`, a copy of `tools/` that `.githooks/post-commit` keeps at the last commit, and the start hook names the `propose.mjs` and `pick.mjs` in that copy, so a change to the tools reaches project sessions once it's committed.
- `.agents/skills/`: byte copies of `.claude/skills/` for agents that read skills there. Edit a skill in `.claude/skills/`; lint reports a copy that differs, and `node tools/lint.mjs --fix` writes it.

## How rules and pages reach the agent

Each domain in `vault.config.json` says which sessions it reaches:

- `markers`: file names, such as a manifest every project of the domain's kind has. A folder holding one is the root of a project in the domain. An edit takes the domains of the nearest marker folder at or above its file. A session takes those at or above its folder, and those of markers up to `reach.markerDepth` (3 by default) folders below it, so a session at a monorepo root is in each package's domain.
- `paths`: this machine's project folders, kept in the untracked `vault.local.json` as `{ "domains": { "<domain>": { "paths": ["<absolute folder>"] } } }`, since folders differ per machine. Lint reports a path that doesn't exist here as an error. The file is the user's to change.
- `everywhere: true`: the domain's pages, keyword rules and `tools` rules reach every session. Its `always` and `applies_to` rules still reach only the sessions its markers and paths put it in.
- `vaultOnly: true`: the domain holds pages only, which sessions in this folder read. `tools/propose.mjs` refuses a rule in it, and lint reports one written any other way as an error, which blocks commits.
- `compile`: a list of adapter names, unset by default. The user runs `node tools/compile.mjs <project>` to write the domain's live file-glob and keyword rules, and global's, into a marked section of the project's `AGENTS.md`, for an agent that has no hooks to deliver them. `compile.maxBytes` in `vault.config.json` caps the section (16,384 by default). Lint errors on a name with no `tools/adapters/<name>/compile.mjs`.

Global reaches every session. A domain that isn't vault-only and reaches no project on this machine gets a lint warning. A domain's project root, the marker folder or the path, is where its globs and picks start. A marker folder in a worktree under `.claude/worktrees/` has the main checkout as its root.

A note `tools/propose.mjs` writes applies at once. A note saved any other way applies once it has gone `delivery.settleSeconds` (60 by default, in `vault.config.json`) without another save, so a rule being typed in Obsidian doesn't reach sessions half-written. The hooks read each note as it is now:

- `always: true` rules load at the start of every session the domain reaches and of each subagent in it, and a session already running gets one with its next prompt.
- Rules with `applies_to` refuse the first matching edit to each file by each agent in a session, the session's own and each subagent. The one refusal carries every rule and page due on that file: the first `delivery.maxRulesPerEdit` rules (3 by default) in full, as many as fit in `delivery.maxBlockChars` (1,200 characters), the rest as one-line pointers. The retry goes through.
- Rules with `keywords` are shown when a prompt mentions one of them.
- Rules with `tools` refuse the first call to a tool they name by each agent in a session, with every rule due on that tool in the one refusal. The retry goes through.
- At the end of a turn, the Stop hook checks the files in a git project that changed since the turn began and that no Edit or Write call reached through the edit hook this turn, such as a file a shell command wrote. It shows the rules with `applies_to` due on each one, testing `triggers` against the whole file, and the turn goes on so the agent re-reads its change against them. A shell write to a file an edit already reached this turn isn't checked.

Taste and knowledge rules arrive the same five ways.

Each session gets a rule once, again after its Do, Not or Because changes, or a knowledge rule's `as_of`, again when its label changes, and again after compaction or `/clear`. A label comes after the rule's text. `source changed on <date>` means a source the note cites has a newer copy, fetched that day, that the note doesn't cite yet, or `source changed` when no newer copy has a valid fetched day: check the fact against the new copy, then propose again with `repeats` and a quote from it, or retire the note. `version unknown` means the note's `requires` couldn't be checked against the project's lockfile. A note with a lint error, or with `superseded_by`, is never delivered; `index.md` marks the first kind `not delivered` with its error.

A page with `keywords` or `applies_to` comes up as a pointer, its key, kind, summary and path, when a prompt mentions one of its keywords or an edit touches a file its globs match. On an edit, an unseen page refuses the first edit like a rule and rides in the same refusal, the pages past `delivery.maxPages` (3 by default, in `vault.config.json`) without their summaries; on a prompt, at most `delivery.maxPages` come up at a time. Each session, and each subagent in it, gets a page once, and again after compaction or `/clear`. A domain's pages reach the sessions it reaches, global's and an `everywhere` domain's reach every session, and a session in this folder gets every domain's, a vault-only domain's among them.

Every session start also names the topics of global, the session's domains and the `everywhere` domains (the listed ones, then the others rules and pages have) and points to `index.md`, so the agent reads the pages on a topic its task touches. A session in this folder hears every domain's topics.

Each hook's output stays within `delivery.maxContextChars` (8,000 by default), since the agent turns a longer one into a file path. It fills in rank order: errors, always rules, matched rules, pages, topics. A closing line counts what it left out and points to `index.md`. What a hook leaves out comes up again later, except the rules a refusal or the Stop hook leaves out: that file doesn't bring them up again.

A new or resumed session also hears, in one line each, how many errors were logged in `.state/errors.log` since `/lint` last ran, and when `/lint` last ran and how many notes changed since, once one has and either `lint.remindAfterDays` (14 by default) have passed or `lint.remindAfterNotes` (10) notes have changed, both in `vault.config.json`. The notes a `/lint` run changes before its last step, `node tools/review.mjs done`, don't count. Both lines repeat until `/lint` runs. A third line names the notes of the domains whose topics it hears that an error keeps from delivery, up to three with their first error, and repeats until they're fixed; a session in this folder hears of every domain's, and of notes outside any domain. A fourth line counts the sources the notes of those domains and global cite that haven't been checked within `knowledge.checkAfterDays` (14 by default), and repeats until `/lint` refreshes them.

## Rule notes

```markdown
---
type: rule
domain: example-ui
kind: taste
basis: stated
topic: code
always: false
applies_to:
  - 'src/client/UI/**/*.ts'
  - '!src/client/UI/**/*.test.ts'
triggers: []
keywords:
  - typed props
created: 2026-10-19
updated: 2026-10-19
---

**Do:** Type UI props and handlers with named types.
**Not:** Annotate them as `any`.
**Because:** An `any` hides type errors that would show up while editing.

## Examples

## Evidence
- 2026-10-19 · stated · session 1a2b3c4d · "never let any into the UI code" (a-1a2b3c4d)
```

- `kind`: `taste` (the default) or `knowledge`, a fact about an API, version or tool that training gets wrong or doesn't know. Both kinds take the same scope fields: `always`, `applies_to`, `triggers`, `keywords` and `tools`.
- `basis`: `stated` when the user said it, `inferred` when you generalized it from their corrections, `pick` when a recorded answer from an earlier session backs it (a `q-` row in `raw/picks/`), `reading` when your own reading of what you saw backs it. Knowledge rules use `stated`, `failure` (something worked only after a failure) or `source` (a dated source shows it).
- `as_of`: knowledge rules only, the day the fact was last checked, as YYYY-MM-DD: the source's date, or the day it was proposed, moved up when `repeats` adds newer evidence. Delivery shows it, and lint warns once it is more than 180 days old (`knowledge.staleAfterDays` in `vault.config.json`), counting from the last day refresh checked every source the note cites when that is later; a check that found a newer copy counts once the note cites it. A domain sets its own `staleAfterDays` and `checkAfterDays` under `domains.<d>.knowledge`. Taste rules never expire.
- `requires`: optional, knowledge rules and pages only: the package versions the note holds for, as a list shaped like OSV's `affected` entries (https://ossf.github.io/osv-schema/). Each entry has `package` with `ecosystem` and `name`, and `ranges`, each a `type` (`SEMVER` or `ECOSYSTEM`) and `events` such as `introduced: '2.0.0'` and `fixed: '3.0.0'`. Lint checks the shape and the SEMVER versions. A domain's `readers`, extensions in `tools/ext/readers/`, read the versions from a project's lockfile: a note the lockfile rules out isn't delivered there, and one no reader can check is delivered labelled `version unknown`.
- `topic`: a short topic, ideally one the domain's other rules have or `vault.config.json` lists for it. Lint warns on a rule with no topic unless it's superseded. Among delivered rules, it also warns on a topic only one rule in its domain has that the config doesn't list. Global topics aren't checked against the config. `/lint` reports the listed topics no rule has yet.
- `always`: only for short rules that matter in nearly every session. The user sets it in Obsidian; `tools/propose.mjs` refuses it. Lint warns on a knowledge rule with `always` longer than the 300 characters a taste rule may have.
- `applies_to`: globs relative to the domain's project root; global's are read from the file's project root, or from the session's folder when no domain has the file. `**` crosses folders, `*` doesn't, `{a,b}` picks one. Matching ignores case and worktree folders.
  - An entry starting with `!` excludes the files it matches. Entries apply in order, as in a `.gitignore`: the last one that matches a file decides. A list with no plain entry matches nothing, and lint reports a `!` entry with nothing before it to exclude from as an error.
  - `'<namespace>:<glob>'` matches names in a namespace other than files, such as objects in a running app. `namespaces` in `vault.config.json` declares each, with its `separator` and `escape` character, and lint reports an undeclared one as an error. The `escape` is one character, not a glob character (`* ? [ ] { } , !`) and not in the `separator`. `file:` is the same as no prefix. Names in a namespace match with case; file globs ignore it.
  - A tool other than Edit, Write, MultiEdit and NotebookEdit edits names once `editTools` in `vault.config.json` maps it, as `{ "<tool>": { "namespace": "<ns>", "path": "tool_input.<field>", "after": "tool_input.<field>" } }`: `path` is the input field holding the name it edits, and `after` the one holding the new text `triggers` test. A name takes the session's domains, since it has no project folder. Lint reports an entry for a file tool, or for a tool the edit hook's matcher never sends it, as an error.
  - A domain's `aliases`, `{ "<ns>": "<name>" }`, maps a name in the namespace to a file through `tools/ext/aliases/<name>.mjs`, in projects that have what it reads. The edit then matches the file's globs too, so one rule can cover both.
- `triggers`: optional regexes tested against the new text of an edit, or against the input of a call `tools` names as JSON text, so `^` anchors at `{` and quotes and newlines in it are escaped. When present, the rule applies only if one matches. A rule a mapped call reaches through both `applies_to` and `tools` applies when either text matches.
- `keywords`: optional words or phrases that bring the rule up from a prompt.
- `tools`: optional, exact tool names, each agent's own, such as `AskUserQuestion` or an MCP tool's full name. Lint checks them against every adapter that `agents` in `vault.config.json` lists (`claude-code` when unset), and reports a name the edit hook's matcher never sends it, such as `Bash`, or one that edits a file, such as `Edit`, as an error: give a rule on files `applies_to` instead. These checks are lint's only; the hooks deliver the rule whatever `agents` lists.
- Every rule needs `always`, `applies_to`, `keywords` or `tools`; lint reports one with none as an error.
- `superseded_by`: optional, the note that replaces this one, as a link or a key like `example-ui/new-slug`. The old note stays in the vault and the index, and the hooks stop delivering it. Deleting a note retires its rule too.
- Single-quote globs and regexes so Obsidian reads them as text and keeps a namespace's backslash escapes.
- Single-quote any list item that holds `: ` or would read as a number or `true`. YAML reads the first as a key and value and the second as no text, and lint reports either as the note's error, so the note isn't delivered.
- `tools/propose.mjs` refuses a field it doesn't take, such as `tools` or `requires`; add those to the note it writes.
- `**Do:**` and `**Not:**` are required, one line each. Pair every "never X" with an "instead Y". `**Because:**` gives the user's reason; leave it empty rather than invent one. Keep the three lines together under 300 characters for a taste rule and 600 for a knowledge rule, counting the "As of" date a knowledge rule is delivered with (`delivery.maxRuleChars` and `delivery.maxKnowledgeRuleChars`). The hooks cut a rule at its cap.
- `## Evidence` has one line per source: date, kind (`stated` or `correction`; `choice` for a pick), the session's short name, the user's exact words, and the proposal id. A `choice` line also names the options the user passed over and the question, and ends with the pick's id and the proposal id. A `failure` line gives the file, the error as a tool printed it and `fixed by:` the fix; a `source` line gives the URL or `raw/refs/` file, `dated` its date, and its exact words. An `agent's reading` line gives your reading in your own words, unquoted. A `stated` line quoting a page with `author: user` gives the page's path where the session goes: `- 2026-10-19 · stated · wiki/example-ui/concepts/grid.md · "the grid is 8px" (a-1a2b3c4d)`.
- Link notes by their path from the vault root, `[[wiki/<domain>/<folder>/<slug>|<slug>]]`.

## Pages

Pages hold knowledge in the agent's words, or with `author: user` the user's own; What belongs here says what counts. Sessions find them through `index.md`, and the hooks point a session to one whose `keywords` or `applies_to` match its work. Each page has one `kind`:

- **topic**: sums up what the vault knows on one topic: how its rules and pages fit together, the sources behind them, and what's still open. It links each other page on its topic, source pages included. Each topic in a domain has at most one; `/ingest`, `/lint` and a filed-back answer update it, and start it when the topic has none. Name it after its topic.
- **concept**: one idea, technique or API, explained.
- **entity**: one named thing, such as a library, tool, service or game.
- **synthesis**: an answer or comparison a session worked out from the vault and filed back, so a later session can reuse it.
- **source** (`sources/source-<slug>.md`): one source, what it says, and the user's words about it. `/ingest` writes it.

Check `index.md` that no note has the slug before you start a page.

```markdown
---
type: page
domain: example-ui
kind: source
topic: layout
summary: Shop screens the user liked and what they said about the spacing.
source: raw/refs/shop-screens.png
source_date: 2026-09-30
created: 2026-10-22
updated: 2026-10-22
---

## You said
- 2026-10-22 · session 1a2b3c4d · "the cards breathe, the tabs feel cramped"

## Agent's reading
What the source shows, by topic, in the agent's words.

## Rules
- [[wiki/example-ui/rules/roomy-cards|roomy-cards]]
```

- `kind`: required, one of the five above. `index.md` labels each page with it, as `source page`, `topic page` and so on. Lint warns on a page without one.
- `author`: `agent`, the default, or `user` for the user's own writing, in any kind. On a page with `author: user` you may only add lines under `## Agent notes`, appending that heading at the end when the page has none. The section runs to the next `#` or `##` heading. The lines you add may hold `###` headings but no `#` or `##` one, and may not move where the section ends, as an unclosed code fence would. The edit hook denies any other change to the file, with no retry, and denies adding or removing `author: user`, which only the user sets. Lint asks it for no `topic` or `summary`, and `lint --fix` leaves it as it is. Its text, without the frontmatter and `## Agent notes`, is the user's words: a rule may quote it as `basis: stated`, with `page:` its path and `quote:` the words.
- `topic`: the topic the page belongs under in `index.md`, like a rule's. Lint warns on a page with none.
- `summary`: one line on what the page holds, shown in `index.md` and when a hook points to the page. Lint warns on a page with none. Single-quote it if it holds ` #`, which YAML reads as a comment.
- `keywords`: optional, the words or phrases a request on the page's subject would use. A prompt that mentions one brings the page up.
- `applies_to`: optional globs, written as a rule's. An edit to a matching file brings the page up. A vault-only domain's pages reach no edit, so lint warns on one with `applies_to`.
- `triggers`: optional, as a rule's: an edit to a matching file brings the page up only when its new text matches one.
- `always`, `tools` and `requires`: optional, as a rule's. Nothing delivers `always` or `tools` on a page yet.
- `source`: source pages, a URL, a file under `raw/` that exists, or a bundle's folder, written without a trailing slash. Lint warns on a source page with none.
- `source_date`: optional, when the source was published or last updated, as YYYY-MM-DD. Only source pages take `source` and `source_date`; lint warns on another page with either.
- `updated`: the day the page last changed. Set it whenever you change a page. Lint warns on a page other than a source page when a rule it links under `## Rules` or a source page it cites changed after it, and on a topic page when any source page on its topic did, going by `updated` or, since Obsidian doesn't change `updated`, the day the file was last saved.
- A source page has `## You said`, `## Agent's reading` and `## Rules`, and a topic page `## Rules`, even when one is empty. Lint warns on a missing one.
- `## You said`: source pages, the user's exact words about the source, one line each with the date and the session's short name. Empty when they said nothing. Lint warns on a line in another form, and on a line whose quote isn't in what the user typed in that session. A line whose session is no longer registered, or whose transcript is gone, can't be checked, and lint counts it in its tally of such quotes (see Evidence).
- `## Agent's reading`: source pages, the agent's description. It backs a rule only as `basis: reading`, so the rule's note labels it as the agent's.
- `## Rules`: the rules the page draws on. A source page's rules link back under their `## Examples`. A topic page may have none yet, which says no taste is captured on its topic.
- The other pages' bodies are free: write what a session working on the topic should know.
- Cite each claim a source backs with a footnote that names the source: a file under `raw/` or a URL, then its date when it has one. A source page's own source needs none. `index.md` counts the sources a page's footnotes name and the source pages it links. Lint warns on a footnote that names neither, a citation with no footnote, and a footnote nothing cites.

  ```markdown
  The tab bar packs six tabs into the top strip.[^1] A flex container spaces them with its `gap`.[^2]

  [^1]: raw/refs/shop-screens.png · dated 2026-09-30
  [^2]: https://developer.mozilla.org/en-US/docs/Web/CSS/gap
  ```

- A footnote may end in a locator: `#page=3` for a PDF, `#t=00:12:31` for audio or video, `#L10-L20` or `#L10` for lines of a text file. An anchor in derived text is a line of its own, so a `[p. 3]` inside a sentence is text. Lint warns on a line range past the file's end, and on a page or time the source's derived text has no anchor for.
- A **bundle** is a folder under `raw/refs/` holding a `source.md`: one source, however many files it holds. Its `source.md` starts with frontmatter giving the `commit` it was taken at with its `url` or `repo`, or a `sha256` list of `'<hash>  <path>'` lines, one per file, as `sha256sum` writes them. A footnote cites a file in it by its path. `node tools/bundle.mjs raw/refs/<folder>` writes its `source.md`, with `--url` or `--repo` and `--commit` for a folder taken from a repository, or the `sha256` list without them; it refuses a folder that already has one. A **doc set** is a folder under `raw/refs/` holding an `llms.txt` and no `source.md`, also one source: save its manifest and the pages notes cite, not the rest.
- **Derived text**, `derived/<sha256>.md`, is the text of a binary source: frontmatter giving its `kind` (`pdf`, `video`, `audio` or `image`), `extractor`, `extractor_version` and `source`, the binary's path under `raw/`, then the text with anchors such as `[p. 3]` and `[t=00:12:31]`. `node tools/extract.mjs <file>` writes it, and replaces it when the extractor or its version has changed (`--force` extracts again); it is never edited by hand. Lint warns when a listed extractor's version has moved on from the one that made the text, naming the command to run. Quotes from a binary are checked against its derived text, without the anchor lines, so a quote may run across a page break.

- Log each operation once, from the vault folder, or from anywhere with the paths in full. Each adds one line to `log.md` and rebuilds `index.md`:
  - a page written or changed on its own: `node tools/log.mjs wiki/<domain>/<folder>/<slug>.md`
  - an ingest: `node tools/log.mjs ingest <source> <page>...`, with `--batch` after `ingest` when the source is one of a batch
  - an answer filed back: `node tools/log.mjs query "<question>" <page>...`
- Lint warns, outside code and the user's quoted words, on a link that no note or other markdown file in the vault answers, on a bare `[[slug]]` more than one note has, and on a link by a note's key or through a folder it isn't in, giving the path to write. It reads a markdown link that starts with `./` or `../` from the note's folder, and any other link from the vault root. It also warns on two topic pages on one topic in a domain, and on a page other than a topic page that no other note links, with a `[[link]]` or a markdown link to its `.md` file.

## Picks

A pick is the user's choice between options the agent showed them for one piece of work in a domain's project, such as a screen's layout. It holds for that piece; a rule comes from it only when it says something for every piece, through `basis: pick`. `tools/pick.mjs` writes the rows; `node tools/pick.mjs --help` lists the fields.

```json
{"id":"q-1a2b3c4d","at":"2026-10-21T10:00:00.000Z","source":"pick","session":"…","transcript":"…","cwd":"…","domain":"example-ui",
 "project":"C:/projects/shop-game","subject":"shop","question":"Which shop layout?","header":null,
 "options":[{"label":"A, Grid","description":"…"},{"label":"B, Featured shelf","description":"…"}],"multiSelect":false,
 "pick":"B, Featured shelf","notes":"the featured rod reads first on phone","reason":null,"status":"user","sheet":"raw/picks/2026-10-21-shop.png"}
```

- `domain`: the domain the pick is for. A session in one domain gets it by default; one in several, such as a session at a monorepo root, must give it, and it must be one of the session's.
- `project`: that domain's project root, its marker folder or path, by default. When the domain has several roots in the session, as at a monorepo root, give it: the full path, or a folder name that names one root alone. A confirmation takes its pick's domain and project; a replacement must give the same ones.
- `subject`: the piece of work, lowercase-kebab-case.
- `status`: `user` when the user picked, `provisional` when the agent picked alone while they were away. `notes` is the user's words verbatim, so a provisional pick has none; `reason` is the agent's own. `tools/pick.mjs` refuses `notes`, on a pick or a confirmation, and a comment's `text` that the user didn't type in this session, and refuses both when the session has no transcript.
- `replaces`: the id of the pick this one reverses. A provisional pick can replace only another provisional pick. `confirms`: the id of the provisional pick the user agreed with; the row repeats its question, options, pick and sheet, and its reason unless it gives one. Either one ends the earlier row's turn: a row is live until a later row names it, and only a live row can be named.
- A comment row has `subject` and `text`, the user's words about the piece, and no options.
- `node tools/pick.mjs show <session-id> <subject> [domain [project]]` prints the live picks and comments on the subject in that project, newest first, then the delivered taste and knowledge rules of the domain and of every other domain whose project holds that one, each leaving out the topics in its `showSkipTopics` in `vault.config.json`. The rules it prints count as shown to the session. The builder runs it before building or reviewing the piece and pastes its output into the reviewer's prompt.
- A sheet, a `.png`, `.jpg`, `.jpeg` or `.webp` image or a file with derived text (one saved in `raw/refs/` and extracted), is copied into `raw/picks/`, refused over `picks.maxSheetBytes` (3 MB by default, in `vault.config.json`).
- A provisional, replaced or confirmed pick backs no rule; propose from the live row instead.
- `review.mjs status` lists provisional picks not yet confirmed. Lint warns on a `replaces` or `confirms` that names no row, and on a sheet that doesn't exist.

## What belongs here

- **Rules** are one-line Do/Not taste, and facts training gets wrong, that the hooks deliver. Propose a rule only for what the project's own agent instructions, such as CLAUDE.md, AGENTS.md or `.claude/rules/`, don't already say. A compiled taste-vault section in them is the vault's copy, not the project's own.
- **Pages** are knowledge: concepts, APIs, comparisons, what sources say, and research on any topic, including the background a rule's one line leaves out.
- **Procedures and how-tos**, steps an agent follows, belong in skills; a page may link one. **Project facts**, such as how one project is built or where its files live, belong in that project's CLAUDE.md, docs or auto memory.

## Operations

- **Propose**: in domain sessions the start hook tells you how to propose a rule with `tools/propose.mjs` when the user corrects you, or when a failure or a dated source shows a fact your training gets wrong. In this folder, a session proposes for any domain, as `/ingest` does. `node tools/propose.mjs --help` lists the fields. It writes the note, which applies from then on, and you end your reply with the lines it prints, so the user sees the rule and can edit or delete it. When the rule may repeat ones in the vault, or its words already back another note, it lists them, each marked shown or not shown in this session since its last compaction, and refuses once: propose again with `repeats` set to the rule it repeats, and propose.mjs adds its Evidence line to that note, or propose again as it is if it says something new. Once it writes the note, it names the rules on the same topic whose `applies_to` covers files the new rule's does, so you check the two don't contradict.
- **Re-propose a recorded answer**: a pick or comment that was never turned into a rule can back one from any later session: `basis: pick` with the row's id in `pick`. The row's words are the evidence, so nothing has to be typed again. A row backs one note; proposing it again is refused.
- **Record a pick**: in domain sessions the start hook tells you how to record each pick and comment with `tools/pick.mjs`, and to run its `show` before building or reviewing a piece that has picks.
- **Ingest**: the user runs `/ingest` in this folder with a source: a file, or a URL whose text it saves to `raw/refs/`. You go through it together; it becomes a source page, what they say about it becomes taste rules and the dated facts they keep knowledge rules, and every topic, concept and entity page it touches is updated. Before going through a source, `/ingest` extracts a binary's text and scans every source, a bundle's files each, for key- or token-shaped text, and stops on either until the user decides. An image no extractor reads isn't a stop: its text goes unscanned, the user is told, and it backs `basis: reading` only. `/ingest batch` takes in, without the user, every file `node tools/review.mjs sources` lists, leaves for the user each one either step stops on, and asks before adding any rule.
- **Query**: when asked what the user prefers or what the vault knows, or when a task touches a topic the session start names, read `index.md`, then the pages and notes on the topic. To find notes by their words rather than their topic, run `node tools/search.mjs "<words>"`; `--help` lists its filters. Every rule in the vault is the user's taste; a rule with `basis: inferred` is your generalization of their corrections, and one with `basis: reading` is your reading of what they showed you, so say so when you lean on either.
- **File back**: when an answer drawn from the vault would help a later session, from any session, add it to the page it extends, or file it as a synthesis page and link that from the topic's page, then log the question and every page you changed with `node tools/log.mjs query "<question>" <page>...`.
- **Lint**: the user runs `/lint` in this folder for a check of the whole wiki: lint findings, hook errors, rules corrected again in later sessions, rules no session was shown, contradictions, repeats, listed topics no rule has yet, stale pages, concepts with no page, claims a newer source overrides, gaps worth a web search, and files in `raw/refs/` no source page names yet. Its first step, `node tools/refresh.mjs`, checks each saved source against its URL or repo and saves a new copy of each one that changed, and offline reports the failed checks and goes on; a note citing an older copy is labelled `source changed on <date>` until it cites the new one. Refresh never runs on its own. The next step, `node tools/review.mjs status`, records the run, which quiets the session-start error line and reminder, and logs its lint tally in `log.md`. `node tools/lint.mjs` on its own checks the notes and the generated files, warns on a compiled section in a project of a `compile` domain that is missing, stale or edited by hand and names the `node tools/compile.mjs` command to run, and with `--fix` rewrites the link, footnote and source paths it gives the spelling of, outside the user's quoted words, and rebuilds the generated files; the pre-commit hook rebuilds the generated files and runs it, runs the tests in `test/` when the commit changes `tools/`, `test/`, `hooks/`, `.githooks/` or `.claude-plugin/`, and refuses a commit that rewrites, renames or removes a file in `raw/` unless `VAULT_ALLOW_RAW_CHANGES=1` is set.

## Evidence

- A stated preference or a correction from one session is enough for a rule.
- Cite what backs each rule as it is: the user's words, the error a tool printed and its fix, a dated source and its words, or your own reading. Quote the user's or the source's exact words, marking words left out with …, and give anything else as your reading: `tools/propose.mjs` refuses a quote the user never typed in this session, one a text file under `raw/refs/` or a binary's derived text doesn't hold, one against a binary with no derived text, a source quote against an image, which backs `basis: reading` only, or one the user's page it cites doesn't hold, and lint warns on each such quote already in a note. Lint checks a quote whose transcript is gone against the `raw/inbox/` row that recorded it, and counts in one warning the quotes it can't check, those citing a URL or a gone session with no row; `node tools/review.mjs status` lists them.
- When evidence conflicts, show the user both sides with the one you recommend first, say what decided it, and let them decide. Between taste rules, prefer the stronger basis (`stated`, then `pick`, then `inferred`, then `reading`), then the one with more Evidence lines, then the newer evidence. Between knowledge rules, prefer the one that matches the project's version, then the newer `as_of`. A taste rule and a knowledge rule aren't ranked. For rules whose globs overlap, `node tools/review.mjs status` and `tools/propose.mjs` print this ranking; rank the others yourself. When the two rules' `applies_to` cover different files, keeping both may be the answer.
- The user's own taste beats general best practice. Write rules they expressed, ones a failure or a dated source backs, or your reading of what they showed you, labelled as yours.

## Never

- Change a file that already exists in `raw/`. Put new material in a new file under `raw/refs/`.
- Change the user's words: the quotes under `## Evidence` and `## You said`, and a page with `author: user` outside its `## Agent notes`. Add a line instead.
- Write outside the vault. The one exception is `node tools/compile.mjs`, which the user runs for a project whose domain lists an agent under `compile`; it writes only that project's `AGENTS.md`, inside its marked section. `node tools/agents.mjs <agent>` prints the hooks for the user to install or merge, and writes nothing.

The hooks refuse the first, the edits to a user's page the second forbids, and edits to `active.md`, `index.md`, `decisions.md`, `vault.local.json`, `derived/`, `.state/`, `.sources/` and `.live/`. They guard against mistakes, not deliberate workarounds.

# Agent taste vault

The user's taste and knowledge, kept as a small wiki so Claude Code can apply and look them up. The agent writes rules in session when the user corrects it or a failure or dated source shows what works, and the hooks in `tools/hooks/` deliver them back to the agent from then on. Pages hold knowledge in the agent's words, and sessions read them through `index.md` or when a hook points to one. The user reads, edits and deletes the notes in Obsidian.

## Layout

- `raw/` holds sources and is append-only.
  - `raw/inbox/<date>.jsonl`: rules the agent proposed in session (`source: agent`, `a-` ids), written by `tools/propose.mjs`. Older rows, with `c-` and `p-` ids, are preferences captured from sessions before proposals existed.
  - `raw/picks/<date>.jsonl`: the user's picks between options and their comments on one piece of work, word for word, with `q-` ids, written by `tools/pick.mjs` (see Picks). Rows with no `subject` are questions captured alongside those older inbox rows. The sheet a pick was made from sits beside them as `<date>-<subject>.<ext>`.
  - `raw/refs/`: references the user collects, and the text of web pages `/ingest` saved, each starting with frontmatter that gives its `url` and the day it was `fetched`. A page a browser saved whole, `<name>.html` with the files it shows in `<name>_files/`, is one source, named by its `.html`. You may add new files here.
- `wiki/<domain>/<folder>/<slug>.md`: one rule per note, or a page (see Pages), in its domain's folder for its kind: `rules/`, or `topics/`, `concepts/`, `entities/`, `syntheses/` or `sources/`. A note's key is `<domain>/<slug>` whichever folder holds it, so a slug is used once in a domain: lint reports two notes with one as errors, and neither is delivered. A note in another folder is still read as its frontmatter says, and lint warns. Domains and their project folders are in `vault.config.json`. Rules in `wiki/global/` apply in every project. A **research domain** has `projects: []` and holds pages only, which you read from this folder. `tools/propose.mjs` refuses a rule in it, since no project session would get it, and lint reports one written any other way as an error, which blocks commits.
- `active.md`, `index.md` and `decisions.md`: generated by `node tools/build.mjs`, which each session start and each pick also run. `index.md` lists every page and rule by topic: the topic's pages first, by kind with the topic page leading, each with how many sources it draws on and its summary, then its rules. `decisions.md` lists the picks and comments by domain, project and subject, newest first, with their sheets.
- `log.md`: the notes `tools/propose.mjs` wrote or added evidence to, the operations `tools/log.mjs` logged (a page changed on its own, an ingest, an answer filed back) and each `/lint` run's tally, newest last. Older entries record confirmations, retirements, drops and review decisions from before rules went live on writing.
- `.state/`: the hooks' bookkeeping, including which rules and pages each session was shown.
- `tools/`: the hooks and scripts. Read `tools/CODING_STANDARDS.md` before changing them. Sessions run the hooks from `.live/tools/`, a copy of `tools/` that `.githooks/post-commit` keeps at the last commit, so a change to a hook reaches sessions once it's committed.

## How rules and pages reach the agent

A note `tools/propose.mjs` writes applies at once. A note saved any other way applies once it has gone `delivery.settleSeconds` (60 by default, in `vault.config.json`) without another save, so a rule being typed in Obsidian doesn't reach sessions half-written. The hooks read each note as it is now:

- `always: true` rules load at the start of every session in the domain's projects, and a session already running gets one with its next prompt.
- Rules with `applies_to` refuse the first matching edit to each file in a session and show the rule. The retry goes through.
- Rules with `keywords` are shown when a prompt mentions one of them.

Each session gets a rule once, and again after its Do, Not or Because changes, or a knowledge rule's `as_of`. A note with a lint error, or with `superseded_by`, is never delivered; `index.md` marks the first kind `not delivered` with its error.

A page with `keywords` or `applies_to` comes up as a pointer, its key, kind, summary and path, when a prompt mentions one of its keywords or an edit touches a file its globs match. A page never refuses an edit, and comes up on one only when no rule refuses it. Each session, and each subagent in it, gets a page once, and again after compaction, and at most `delivery.maxPages` (3 by default, in `vault.config.json`) at a time. A project domain's pages reach its projects' sessions, global's reach every session, and a session in this folder gets every domain's.

Every session start also names the topics of global and the session's domains (the listed ones, then the others rules and pages have) and points to `index.md`, so the agent reads the pages on a topic its task touches. A session in this folder hears every domain's topics.

A new or resumed session also hears, in one line each, how many errors were logged in `.state/errors.log` since `/lint` last ran, and when `/lint` last ran and how many notes changed since, once one has and either `lint.remindAfterDays` (14 by default) have passed or `lint.remindAfterNotes` (10) notes have changed, both in `vault.config.json`. The notes a `/lint` run changes before its last step, `node tools/review.mjs done`, don't count. Both lines repeat until `/lint` runs. A third line names the notes of global and the session's domains that an error keeps from delivery, up to three with their first error, and repeats until they're fixed; a session in this folder hears of every domain's, and of notes outside any domain.

## Rule notes

```markdown
---
type: rule
domain: roblox-ui
kind: taste
basis: stated
topic: code
always: false
applies_to:
  - 'src/client/UI/**/*.luau'
triggers: []
keywords:
  - strict
created: 2026-10-19
updated: 2026-10-19
---

**Do:** Start every UI script with `--!strict`.
**Not:** Leave scripts in nonstrict mode.
**Because:** Type errors should show up while editing, not in play tests.

## Examples

## Evidence
- 2026-10-19 · stated · session 1a2b3c4d · "I want the agent to always write scripts in !strict" (a-1a2b3c4d)
```

- `kind`: `taste` (the default) or `knowledge`, a fact about an API, version or tool that training gets wrong or doesn't know. Knowledge rules reach the agent only on matching edits, so they need `applies_to` and take no `keywords` or `always`.
- `basis`: `stated` when the user said it, `inferred` when you generalized it from their corrections, `pick` when a recorded answer from an earlier session backs it (a `q-` row in `raw/picks/`, or an older `c-`/`p-` row in `raw/inbox/` that holds the user's own words), `reading` when your own reading of what you saw backs it. Knowledge rules use `stated`, `failure` (something worked only after a failure) or `source` (a dated source shows it).
- `as_of`: knowledge rules only, the day the fact was last checked, as YYYY-MM-DD: the source's date, or the day it was proposed, moved up when `repeats` adds newer evidence. Delivery shows it, and lint warns once it is more than 180 days old (`knowledge.staleAfterDays` in `vault.config.json`). Taste rules never expire.
- `topic`: a short topic, ideally one the domain's other rules have or `vault.config.json` lists for it. Lint warns on a rule with no topic unless it's superseded. Among delivered rules, it also warns on a topic only one rule in its domain has that the config doesn't list. Global topics aren't checked against the config. `/lint` reports the listed topics no rule has yet.
- `always`: only for short rules that matter in nearly every session. The user sets it in Obsidian; `tools/propose.mjs` refuses it.
- `applies_to`: globs relative to the project root. `**` crosses folders, `*` doesn't, `{a,b}` picks one. Matching ignores case and worktree folders.
- `triggers`: optional regexes tested against the new text of an edit. When present, the rule applies only if one matches.
- `keywords`: optional words or phrases that bring the rule up from a prompt.
- `superseded_by`: optional, the note that replaces this one, as a link or a key like `roblox-ui/new-slug`. The old note stays in the vault and the index, and the hooks stop delivering it. Deleting a note retires its rule too.
- Single-quote globs and regexes so Obsidian reads them as text.
- `**Do:**` and `**Not:**` are required, one line each. Pair every "never X" with an "instead Y". `**Because:**` gives the user's reason; leave it empty rather than invent one. Keep the three lines under 300 characters together, counting the "As of" date a knowledge rule is delivered with.
- `## Evidence` has one line per source: date, kind (`stated` or `correction`; `choice` for a pick), the first 8 characters of the session id, the user's exact words, and the proposal id. A `choice` line also names the options the user passed over and the question, and ends with the pick's id and the proposal id. A `failure` line gives the file, the error as a tool printed it and `fixed by:` the fix; a `source` line gives the URL or `raw/refs/` file, `dated` its date, and its exact words. An `agent's reading` line gives your reading in your own words, unquoted.
- Link notes by their path from the vault root, `[[wiki/<domain>/<folder>/<slug>|<slug>]]`.

## Pages

Pages hold knowledge in the agent's words; What belongs here says what counts. Sessions find them through `index.md`, and the hooks point a session to one whose `keywords` or `applies_to` match its work. Each page has one `kind`:

- **topic**: sums up what the vault knows on one topic: how its rules and pages fit together, the sources behind them, and what's still open. It links each other page on its topic, source pages included. Each topic in a domain has at most one; `/ingest`, `/lint` and a filed-back answer update it, and start it when the topic has none. Name it after its topic.
- **concept**: one idea, technique or API, explained.
- **entity**: one named thing, such as a library, tool, service or game.
- **synthesis**: an answer or comparison a session worked out from the vault and filed back, so a later session can reuse it.
- **source** (`sources/source-<slug>.md`): one source, what it says, and the user's words about it. `/ingest` writes it.

Check `index.md` that no note has the slug before you start a page.

```markdown
---
type: page
domain: roblox-ui
kind: source
topic: layout
summary: Shop screens the user liked and what they said about the spacing.
source: raw/refs/shop-screens.png
source_date: 2026-09-30
created: 2026-10-22
updated: 2026-10-22
---

## You said
- 2026-10-22 · session 1a2b3c4d · "the cards breathe, the tabs feel cramped"

## Agent's reading
What the source shows, by topic, in the agent's words.

## Rules
- [[wiki/roblox-ui/rules/roomy-cards|roomy-cards]]
```

- `kind`: required, one of the five above. `index.md` labels each page with it, as `source page`, `topic page` and so on. Lint warns on a page without one.
- `topic`: the topic the page belongs under in `index.md`, like a rule's. Lint warns on a page with none.
- `summary`: one line on what the page holds, shown in `index.md` and when a hook points to the page. Lint warns on a page with none. Single-quote it if it holds ` #`, which YAML reads as a comment.
- `keywords`: optional, the words or phrases a request on the page's subject would use. A prompt that mentions one brings the page up.
- `applies_to`: optional globs, written as a rule's. An edit to a matching file brings the page up. A research domain's pages reach no edit, so lint warns on one with `applies_to`. Lint also warns on a page with `always` or `triggers`, which only rules take.
- `source`: source pages, a URL or a file under `raw/` that exists. Lint warns on a source page with none.
- `source_date`: optional, when the source was published or last updated, as YYYY-MM-DD. Only source pages take `source` and `source_date`; lint warns on another page with either.
- `updated`: the day the page last changed. Set it whenever you change a page. Lint warns on a page other than a source page when a rule it links under `## Rules` or a source page it cites changed after it, and on a topic page when any source page on its topic did, going by `updated` or, since Obsidian doesn't change `updated`, the day the file was last saved.
- A source page has `## You said`, `## Agent's reading` and `## Rules`, and a topic page `## Rules`, even when one is empty. Lint warns on a missing one.
- `## You said`: source pages, the user's exact words about the source, one line each with the date and the first 8 characters of the session id. Empty when they said nothing. Lint warns on a line in another form, and on a line whose quote isn't in what the user typed in that session, while the session is still registered and its transcript is there.
- `## Agent's reading`: source pages, the agent's description. It backs a rule only as `basis: reading`, so the rule's note labels it as the agent's.
- `## Rules`: the rules the page draws on. A source page's rules link back under their `## Examples`. A topic page may have none yet, which says no taste is captured on its topic.
- The other pages' bodies are free: write what a session working on the topic should know.
- Cite each claim a source backs with a footnote that names the source: a file under `raw/` or a URL, then its date when it has one. A source page's own source needs none. `index.md` counts the sources a page's footnotes name and the source pages it links. Lint warns on a footnote that names neither, a citation with no footnote, and a footnote nothing cites.

  ```markdown
  The tab bar packs six tabs into the top strip.[^1] A UIListLayout spaces them with its Padding.[^2]

  [^1]: raw/refs/shop-screens.png · dated 2026-09-30
  [^2]: https://create.roblox.com/docs/reference/engine/classes/UIListLayout
  ```

- Log each operation once, from the vault folder, or from anywhere with the paths in full. Each adds one line to `log.md` and rebuilds `index.md`:
  - a page written or changed on its own: `node tools/log.mjs wiki/<domain>/<folder>/<slug>.md`
  - an ingest: `node tools/log.mjs ingest <source> <page>...`, with `--batch` after `ingest` when the source is one of a batch
  - an answer filed back: `node tools/log.mjs query "<question>" <page>...`
- Lint warns, outside code and the user's quoted words, on a link that no note or other markdown file in the vault answers, on a bare `[[slug]]` more than one note has, and on a link by a note's key or through a folder it isn't in, giving the path to write. It reads a markdown link that starts with `./` or `../` from the note's folder, and any other link from the vault root. It also warns on two topic pages on one topic in a domain, and on a page other than a topic page that no other note links, with a `[[link]]` or a markdown link to its `.md` file.

## Picks

A pick is the user's choice between options the agent showed them for one piece of work in a domain's project, such as a screen's layout. It holds for that piece; a rule comes from it only when it says something for every piece, through `basis: pick`. `tools/pick.mjs` writes the rows; `node tools/pick.mjs --help` lists the fields.

```json
{"id":"q-1a2b3c4d","at":"2026-10-21T10:00:00.000Z","source":"pick","session":"…","transcript":"…","cwd":"…","domain":"roblox-ui",
 "project":"C:/Users/Lowle/OneDrive/Desktop/roblox-ui","subject":"shop","question":"Which shop layout?","header":null,
 "options":[{"label":"A, Grid","description":"…"},{"label":"B, Featured shelf","description":"…"}],"multiSelect":false,
 "pick":"B, Featured shelf","notes":"the featured rod reads first on phone","reason":null,"status":"user","sheet":"raw/picks/2026-10-21-shop.png"}
```

- `project`: the domain project folder from `vault.config.json` the session ran in. `subject`: the piece of work, lowercase-kebab-case.
- `status`: `user` when the user picked, `provisional` when the agent picked alone while they were away. `notes` is the user's words verbatim, so a provisional pick has none; `reason` is the agent's own.
- `replaces`: the id of the pick this one reverses. A provisional pick can replace only another provisional pick. `confirms`: the id of the provisional pick the user agreed with; the row repeats its question, options, pick and sheet, and its reason unless it gives one. Either one ends the earlier row's turn: a row is live until a later row names it, and only a live row can be named.
- A comment row has `subject` and `text`, the user's words about the piece, and no options.
- `node tools/pick.mjs show <session-id> <subject>` prints the subject's live picks and comments, newest first, then the domain's delivered taste rules, leaving out the topics in the domain's `showSkipTopics` in `vault.config.json`. The rules it prints count as shown to the session. The builder runs it before building or reviewing the piece and pastes its output into the reviewer's prompt.
- A sheet is copied into `raw/picks/`, refused over `picks.maxSheetBytes` (3 MB by default, in `vault.config.json`).
- A provisional, replaced or confirmed pick backs no rule; propose from the live row instead.
- `review.mjs status` lists provisional picks not yet confirmed. Lint warns on a `replaces` or `confirms` that names no row, and on a sheet that doesn't exist.

## What belongs here

- **Rules** are one-line Do/Not taste, and facts training gets wrong, that the hooks deliver. Propose a rule only for what the project's CLAUDE.md or `.claude/rules/` doesn't already say.
- **Pages** are knowledge: concepts, APIs, comparisons, what sources say, and research on any topic, including the background a rule's one line leaves out.
- **Procedures and how-tos**, steps an agent follows, belong in skills; a page may link one. **Project facts**, such as how one project is built or where its files live, belong in that project's CLAUDE.md, docs or auto memory.

## Operations

- **Propose**: in domain sessions the start hook tells you how to propose a rule with `tools/propose.mjs` when the user corrects you, or when a failure or a dated source shows a fact your training gets wrong. In this folder, a session proposes for any domain, as `/ingest` does. `node tools/propose.mjs --help` lists the fields. It writes the note, which applies from then on, and you end your reply with the lines it prints, so the user sees the rule and can edit or delete it. When the rule may repeat ones in the vault, or its words already back another note, it lists them, each marked shown or not shown in this session since its last compaction, and refuses once: propose again with `repeats` set to the rule it repeats, and propose.mjs adds its Evidence line to that note, or propose again as it is if it says something new. Once it writes the note, it names the rules on the same topic whose `applies_to` covers files the new rule's does, so you check the two don't contradict.
- **Re-propose a recorded answer**: a pick or an older captured message that was never turned into a rule can back one from any later session: `basis: pick` with the row's id in `pick`. The row's words are the evidence, so nothing has to be typed again. A row backs one note; proposing it again is refused.
- **Record a pick**: in domain sessions the start hook tells you how to record each pick and comment with `tools/pick.mjs`, and to run its `show` before building or reviewing a piece that has picks.
- **Ingest**: the user runs `/ingest` in this folder with a source: a file, or a URL whose text it saves to `raw/refs/`. You go through it together; it becomes a source page, what they say about it becomes taste rules and the dated facts they keep knowledge rules, and every topic, concept and entity page it touches is updated. `/ingest batch` takes in, without the user, every file `node tools/review.mjs sources` lists, and asks before adding any rule.
- **Query**: when asked what the user prefers or what the vault knows, or when a task touches a topic the session start names, read `index.md`, then the pages and notes on the topic. To find notes by their words rather than their topic, run `node tools/search.mjs "<words>"`; `--help` lists its filters. Every rule in the vault is the user's taste; a rule with `basis: inferred` is your generalization of their corrections, and one with `basis: reading` is your reading of what they showed you, so say so when you lean on either.
- **File back**: when an answer drawn from the vault would help a later session, from any session, add it to the page it extends, or file it as a synthesis page and link that from the topic's page, then log the question and every page you changed with `node tools/log.mjs query "<question>" <page>...`.
- **Lint**: the user runs `/lint` in this folder for a check of the whole wiki: lint findings, hook errors, rules corrected again in later sessions, rules no session was shown, contradictions, repeats, listed topics no rule has yet, stale pages, concepts with no page, claims a newer source overrides, gaps worth a web search, and files in `raw/refs/` no source page names yet. Its first step, `node tools/review.mjs status`, records the run, which quiets the session-start error line and reminder, and logs its lint tally in `log.md`. `node tools/lint.mjs` on its own checks the notes and the generated files, and with `--fix` rewrites the link, footnote and source paths it gives the spelling of, outside the user's quoted words, and rebuilds the generated files; the pre-commit hook rebuilds the generated files and runs it, runs the tests in `test/` when the commit changes `tools/`, `test/` or `.githooks/`, and refuses a commit that rewrites, renames or removes a file in `raw/` unless `VAULT_ALLOW_RAW_CHANGES=1` is set.

## Evidence

- A stated preference or a correction from one session is enough for a rule.
- Cite what backs each rule as it is: the user's words, the error a tool printed and its fix, a dated source and its words, or your own reading. Quote the user's or the source's exact words, marking words left out with …, and give anything else as your reading: `tools/propose.mjs` refuses a quote the user never typed in this session, or one a text file under `raw/refs/` doesn't hold, and lint warns on one already in a note.
- When evidence conflicts, show the user both sides with the one you recommend first, say what decided it, and let them decide. Between taste rules, prefer the stronger basis (`stated`, then `pick`, then `inferred`, then `reading`), then the one with more Evidence lines, then the newer evidence. Between knowledge rules, prefer the newer `as_of`. A taste rule and a knowledge rule aren't ranked. For rules whose globs overlap, `node tools/review.mjs status` and `tools/propose.mjs` print this ranking; rank the others yourself. When the two rules' `applies_to` cover different files, keeping both may be the answer.
- The user's own taste beats general best practice. Write rules they expressed, ones a failure or a dated source backs, or your reading of what they showed you, labelled as yours.

## Never

- Change a file that already exists in `raw/`. Put new material in a new file under `raw/refs/`.
- Change the user's words: the quotes under `## Evidence` and `## You said`. Add a line instead.
- Write outside the vault.

The hooks refuse the first, and edits to `active.md`, `index.md`, `decisions.md`, `.state/` and `.live/`. They guard against mistakes, not deliberate workarounds.

# Agent taste vault

The user's taste, kept as a small wiki so Claude Code can apply it. A background pass started by the hooks in `tools/hooks/` captures preferences from sessions, and the hooks deliver confirmed rules back to the agent. The user reads and edits the notes in Obsidian.

## Layout

- `raw/` holds sources and is append-only.
  - `raw/inbox/<date>.jsonl`: preferences captured from sessions, written by the session pass.
  - `raw/picks/<date>.jsonl`: every question the agent asked in a domain session and the user answered, word for word: the question, its options, the pick and any notes. Written by the session pass, without the model.
  - `raw/decisions.jsonl`: review decisions, written by `tools/review.mjs`.
  - `raw/judgments/`: the user's picks between design options, verbatim and dated ("B over A because…"). You may add a new file here when the user makes a pick. Unlike `raw/picks/`, which logs every answered question automatically, these are picks you record by hand, usually with the user's reason.
  - `raw/refs/`: references the user collects. You may add new files here.
- `wiki/<domain>/<slug>.md`: one rule per note. Domains and their project folders are in `taste.config.json`. Rules in `wiki/global/` apply in every project.
- `confirmed.json`: the ledger of confirmed rules. Only the hooks write it, when the user types `confirm:` or `retire:` in chat.
- `active.md` and `index.md`: generated by `node tools/build.mjs`.
- `log.md`: confirmations, retirements and reviews, newest last.
- `tools/`: the hooks and scripts. Read `tools/CODING_STANDARDS.md` before changing them.

## How rules reach the agent

A rule takes effect only once the user confirms it. Then:

- `always: true` rules load at the start of every session in the domain's projects.
- Rules with `applies_to` refuse the first matching edit to each file in a session and show the rule. The retry goes through.
- Rules with `keywords` are shown when a prompt mentions one of them.

The hooks deliver the wording recorded when the user confirmed, not the live note. If a confirmed note changes, the old wording stays in force until the user confirms again.

## Rule notes

```markdown
---
type: rule
domain: roblox-ui
status: provisional
basis: stated
topic: code
always: false
applies_to:
  - 'src/client/UI/**/*.luau'
triggers: []
keywords:
  - strict
replaces: []
created: 2026-10-19
updated: 2026-10-19
---

**Do:** Start every UI script with `--!strict`.
**Not:** Leave scripts in nonstrict mode.
**Because:** Type errors should show up while editing, not in play tests.

## Examples

## Evidence
- 2026-10-19 · stated · session 1a2b3c4d · "I want the agent to always write scripts in !strict" (c-1a2b3c4d)
```

- `status`: `provisional`, `confirmed` or `outdated`. Only the user's `confirm:` makes a rule confirmed, and the hook sets the field.
- `basis`: `stated` when the user said it, `inferred` when it comes from their choices or corrections.
- `topic`: one of the domain's topics in `taste.config.json`.
- `always`: only for short rules that matter in nearly every session.
- `applies_to`: globs relative to the project root. `**` crosses folders, `*` doesn't, `{a,b}` picks one. Matching ignores case and worktree folders.
- `triggers`: optional regexes tested against the new text of an edit. When present, the rule applies only if one matches.
- `keywords`: optional words or phrases that bring the rule up from a prompt.
- `replaces`: keys of rules this one supersedes, like `roblox-ui/old-slug`. Confirming this note retires them.
- Single-quote globs and regexes so Obsidian reads them as text.
- `**Do:**` and `**Not:**` are required, one line each. Pair every "never X" with an "instead Y". `**Because:**` gives the user's reason; leave it empty rather than invent one. Keep the three lines under 300 characters together.
- `## Evidence` has one line per source: date, kind (`stated`, `choice` or `correction`), the first 8 characters of the session id, the user's exact words, and the capture or pick id.
- Link notes with `[[wiki/<domain>/<slug>|<slug>]]`.

## Operations

- **Review**: the user runs `/taste-review` in this folder to turn captures into notes.
- **Query**: when asked what the user prefers, read `index.md`, then the notes. Confirmed rules are the user's taste; provisional ones are candidates. Say which is which.
- **Lint**: `node tools/lint.mjs` checks notes, the ledger and the generated files. The pre-commit hook rebuilds the generated files and runs it.

## Evidence

- A stated preference from one session is enough for a provisional note.
- An inferred one needs evidence from 3 sessions before you suggest confirming it.
- Picks from `raw/picks/` back a provisional `basis: inferred` note only once the same leaning shows up in picks from 3 sessions. Their evidence lines use kind `choice` and the pick's `q-` id.
- When evidence conflicts, show the user both sides and let them decide.
- The user's own taste beats general best practice. Don't add rules they didn't express.

## Never

- Edit `confirmed.json`, `active.md`, `index.md`, or existing files in `raw/` or `.state/`.
- Write `status: confirmed`, or change the Do, Not, Because, `applies_to`, `triggers`, `keywords` or `always` of a confirmed note. Write a new note with `replaces:` instead, and ask the user to confirm it.
- Confirm or retire rules yourself, including through a shell command. If the user types `confirm:` and you see it as a normal message, the hooks aren't loaded in this session: tell them to start a new one.

The hooks refuse most of these. They guard against mistakes, not deliberate workarounds.

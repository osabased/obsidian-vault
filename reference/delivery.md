# How rules and pages reach the agent

Each domain in `vault.config.json` says which sessions it reaches:

- `markers`: file names, such as a manifest every project of the domain's kind has. A folder holding one is the root of a project in the domain. An edit takes the domains of the nearest marker folder at or above its file. A session takes those at or above its folder, and those of markers up to `reach.markerDepth` (3 by default) folders below it, so a session at a monorepo root is in each package's domain.
- `paths`: this machine's project folders, kept in the untracked `vault.local.json` as `{ "domains": { "<domain>": { "paths": ["<absolute folder>"] } } }`, since folders differ per machine. Lint reports a path that doesn't exist here as an error. The file is the user's; the `domain` tool adds a session's folder to it only after the user agrees.
- `everywhere: true`: the domain's pages, keyword rules and `tools` rules reach every session. Its `always` and `applies_to` rules still reach only the sessions its markers and paths put it in; elsewhere, an `always` rule with `keywords` comes by its keywords like any keyword rule.
- `vaultOnly: true`: the domain holds pages only, which sessions in the vault folder read. the `propose` tool refuses a rule in it, and lint reports one written any other way as an error, which blocks commits.
- `readers`: names of extensions in `tools/ext/readers/` that read package versions from a project's lockfile, for the notes with `requires` or `checked_with` (see `reference/notes.md`). `global`'s, under `domains.global.readers`, read at every session's project: each root of the session's domains, or for a session in no domain the work tree its folder is in, or the folder itself outside one. An edit to a file in no domain, in a work tree below the session's folder, reads that work tree. A worktree under `.claude/worktrees/` reads as its main checkout. A project reads the nearest lockfile at or above its root within its repository, so a monorepo's root lockfile serves its packages; outside a repository it reads only its own. The vault folder is no project. While no domain has readers, every version is unknown, and `node tools/review.mjs status` says so.
- `compile`: a list of adapter names, unset by default. The user runs `node tools/compile.mjs <project>` to write the domain's live `always`, file-glob and keyword rules, and global's, into a marked section of the project's `AGENTS.md`, for an agent that has no hooks to deliver them. `compile.maxBytes` in `vault.config.json` caps the section (16,384 by default). Lint errors on a name with no `tools/adapters/<name>/compile.mjs`.

Global reaches every session. A session start in a folder no domain reaches, outside the vault folder, sends one line: the session can propose to `global`, and can suggest a domain to the user (see Start a domain in `AGENTS.md`). A folder that `quiet` in `vault.local.json` matches, a list of globs over absolute folder paths such as an app's scratch folders, hears only the first part; lint reports an entry that is no such glob as an error. A domain that isn't vault-only and reaches no project on this machine gets a lint warning. A domain's project root, the marker folder or the path, is where its globs and picks start. A marker folder in a worktree under `.claude/worktrees/` has the main checkout as its root.

A note the `propose` and `keep` tools write applies at once. A note saved any other way applies once it has gone `delivery.settleSeconds` (60 by default, in `vault.config.json`) without another save, so a rule being typed in Obsidian doesn't reach sessions half-written. The hooks read each note as it is now:

- `always: true` rules load at the start of every session the domain reaches and of each subagent in it, and a session already running gets one with its next prompt.
- Rules with `applies_to` refuse the first matching edit to each file by each agent in a session, the session's own and each subagent. The one refusal carries every rule and page due on that file: the first `delivery.maxRulesPerEdit` rules (3 by default) in full, as many as fit in `delivery.maxBlockChars` (1,200 characters), the rest as one-line pointers. The retry goes through.
- Rules with `keywords` are shown when a prompt mentions one of them.
- Rules with `tools` refuse the first call to a tool they name by each agent in a session, with every rule due on that tool in the one refusal. The retry goes through.
- At the end of a turn, the Stop hook checks the files in a git project that changed since the turn began and that no Edit or Write call reached through the edit hook this turn, such as a file a shell command wrote. It shows the rules with `applies_to` due on each one, testing `triggers` against the whole file, and the turn goes on so the agent re-reads its change against them. A shell write to a file an edit already reached this turn isn't checked.

Taste and knowledge rules arrive the same five ways. A session in the vault folder takes rules like any other session: global's, those of the domains its folder is in, and the `everywhere` domains' keyword and `tools` rules. It reads every domain's pages (see below), not their rules. `tools/lib/reach.mjs` holds these routes, and the hooks and the status line all take them from there; an edit takes them for its file's domains.

Each session gets a rule once, by whichever route brings it first, again after its Do, Not or Because changes, or a knowledge rule's `as_of`, again when its label changes, and again after compaction or `/clear`. A label comes after the rule's text. `source changed on <date>` means a source the note cites has a newer copy, fetched that day, that the note doesn't cite yet, or `source changed` when no newer copy has a valid fetched day: check the fact against the new copy, then propose again with `repeats` and a quote from it, or retire the note. `version unknown` means the note's `requires` or `checked_with` couldn't be checked against the project's lockfile. A note with a lint error, other than a `tools` name check, or with `superseded_by` or `retired`, is never delivered, nor is a knowledge rule the project's version rules out; `index.md` marks the first kind `not delivered` with its error.

A page with `keywords` or `applies_to` comes up as a pointer, its key, kind, summary and path, when a prompt mentions one of its keywords or an edit touches a file its globs match. On an edit, an unseen page refuses the first edit like a rule and rides in the same refusal, the pages past `delivery.maxPages` (3 by default, in `vault.config.json`) without their summaries; on a prompt, at most `delivery.maxPages` come up at a time. Each session, and each subagent in it, gets a page once, and again after compaction or `/clear`. A domain's pages reach the sessions it reaches, global's and an `everywhere` domain's reach every session, and a session in the vault folder gets every domain's, a vault-only domain's among them.

Every session start also names the topics of global, the session's domains and the `everywhere` domains (the listed ones, then the others rules and pages have) and points to `index.md`, so the agent reads the pages on a topic its task touches. A session in the vault folder hears every domain's topics.

Each hook's output stays within `delivery.maxContextChars` (8,000 by default), since the agent turns a longer one into a file path. It fills in rank order: errors, always rules, matched rules, pages, topics. A closing line counts what it left out and points to `index.md`. What a hook leaves out comes up again later, except the rules a refusal or the Stop hook leaves out: that file doesn't bring them up again.

A new or resumed session shows the user, not the agent, one status line: the session's domains, how many rules and pages can reach it and its proposals mode, then what waits for the user. That is the open review-queue entries, whichever session queued them, with how many are unattended; the rules past their version in the session's projects, which `/lint` offers to retire (see `checked_with` in `reference/notes.md`); and `no version readers set` when no domain names readers and a rule that reaches the session names a package. Each is left out when there is none. The rule and page counts take the routes the hooks deliver by, so each rule counted is one a prompt, edit or tool call in the session can bring up. A `tools` rule counts when it names a tool the session's agent sends its edit hook, other than one that edits a file. An `applies_to` rule or page of a domain the session isn't in, which an edit to one of that domain's files brings up, isn't counted. In the vault folder the pages are marked `(every domain)`. The proposals mode is the one the `propose` tool keeps to, by the folder the session began in: `ask` in the vault folder, which offers whatever the mode, since `/ingest` and `/lint` go through each change with the user. The `status` tool, which `/vault status` calls and `node tools/status.mjs [session-id]` also runs, prints it again, for the folder its latest prompt came from, with the rules and pages the session has been shown since it started or was last compacted.

A new or resumed session also hears, in one line each, how many errors were logged in `.state/errors.log` since `/lint` last ran, and when `/lint` last ran and how many notes changed since, once one has and either `lint.remindAfterDays` (14 by default) have passed or `lint.remindAfterNotes` (10) notes have changed, both in `vault.config.json`. The notes a `/lint` run changes before its last step, `node tools/review.mjs done`, don't count. Both lines repeat until `/lint` runs. A third line names the notes of the domains whose topics it hears that an error keeps from delivery, up to three with their first error, and repeats until they're fixed; a session in the vault folder hears of every domain's, and of notes outside any domain. A fourth line counts the sources the notes of those domains and global cite that haven't been checked within `knowledge.checkAfterDays` (14 by default), and repeats until `/lint` refreshes them.

## Vault tools

The vault's tools, `propose`, `keep`, `proposals`, `domain`, `pick`, `log`, `search` and `status`, reach a session as MCP tools from the plugin's server, `mcp/launch.mjs`. It imports `.live/tools/mcp/server.mjs` from the vault the plugin's `vault` option names, and runs the script of the same name in `tools/` for each call, with the call's JSON on stdin; it returns what the script prints, or its error text. A session in the vault folder runs the working `tools/`, any other session `.live/tools/`. The plugin is how a Claude Code session gets them, since the hooks the tools need come only with it. `node tools/agents.mjs codex` prints the hooks and a `[mcp_servers.vault]` block for Codex's `config.toml`.

- **Schemas.** The server builds the tool list when a client asks, by running each script with `--schema`, so the list matches the scripts as committed, and sends `notifications/tools/list_changed` when `.live/tools` is rebuilt. A tool's description and schema join every session's context, so they stay small: `test/context-load.test.mjs` caps the whole list at 12,000 characters.
- **Session.** A tool takes no session id. The PreToolUse hook writes a record in `.state/calls/` for each vault tool call, with the call's id and the hook's session. The server takes the session from the record that matches the call's id and refuses a call with none, so a hook that failed, timed out or didn't run costs the call, not the session's identity. It answers only the agents `agents` in `vault.config.json` lists, from the version the vault's tools need.
- **Consent, by the session's agent.** `propose` and `domain` return an offer, with an id and the lines to show the user, unless the mode lets them write at once, which it never does in the vault folder; `proposals` and `domain` offer in the same way. `keep` writes the offer when its `offer` field is the stored lines exactly, and an offer is kept once. Where the client asks the user before running a tool, `keep` and `proposals` carry the marker that makes it ask on every call and show the arguments: Allow once is the consent, and a Deny writes nothing. The call's record holds a hash of its arguments, and the script spends it before any other check and only for those arguments, so the Allow covers what the prompt showed and a refused call can't be run again. The server lets such a call through only when the tool went out marked on the same connection. The hook lets one `keep` through per offer, so a Deny ends the proposal, and `propose` refuses the same text again in that session. Where it doesn't, the offer ends with a code of four characters. `keep` writes only when exactly one typed message follows the offer, that message holds the code as a word, and the agent's reply before it holds the offer's lines, so the user saw what they agreed to. An agent is held to the consent of its own registered kind, so the command line refuses to keep a prompting agent's offer. The rows record which (see Inbox rows in `reference/notes.md`). For what this doesn't stop, see Limits of consent in `AGENTS.md`.
- **The wiki and rule guards.** From a session outside the vault folder, the edit hook refuses any Edit or Write to a note under `wiki/`, and points to `propose`. From any session, the vault folder's included, it refuses an edit that makes a note a new rule, or that changes a rule's frontmatter, compared as a whole, or its Do, Not or Because. Any other change to a rule's body passes this guard, an Evidence line among them. An edit the hook can't follow counts as a change to a rule it touches, and as a new rule when it writes a new file under `wiki/<domain>/rules/`. The folder the session registered in decides, not the edited file's. So a rule, and a page from a project session, change only through `propose` and `keep`. `lint --fix` doesn't write through the edit tool, so neither guard sees it.
- **Page changes.** `propose` with `page`, a path under `wiki/` in the folder its kind goes in, and `text`, the page's whole new text, offers the change in every mode, `corrections` included; under `off`, outside the vault folder, it needs `asked` as a rule does. Its lines show a new page whole, or a diff of a changed one, and `propose` refuses a change whose lines pass `pages.maxOfferChars` (4,000 by default, in `vault.config.json`; a value that isn't a whole number above 0 counts as the default, and lint reports it), so the user can read what they agree to. It runs the checks the edit hook and lint would: a page with `author: user` may only gain lines under `## Agent notes`, a page can't become a rule, and a note error refuses it. `keep` writes the page only while it is as it was when offered, keeping its line endings, and logs it. A session in the vault folder writes pages directly, through the edit tool.
- **Rewording.** `propose` with `change: 'reword'` and `key`, a rule's key, offers new `do`, `not`, `because`, `applies_to`, `keywords` or `checked_with` for that rule, with a basis and evidence as for a new rule. A reword that gives `checked_with` alone takes no basis, since the version comes from a lockfile, not from anyone's words, and adds no Evidence line. Its lines show the rule as it was and as it would be. It is consented to as a new rule is: in `corrections`, from a project session, `propose` writes it at once, and otherwise `keep` does; one that changes `checked_with` is an offer in every mode. The write replaces what the reword gives and sets `updated`; except in a reword that gives `checked_with` alone, it also moves a knowledge rule's `as_of` up and adds the Evidence line.
- **Retiring and moving.** `propose` with `key` and `change: 'retire'` offers to retire the rule, with `because`, why, in one line, and `superseded_by` when another rule replaces it; `keep` writes `retired`, `retired_because` and `superseded_by` into its frontmatter, and the note stays. With `change: 'move'` and `domain`, it offers to move the rule to that domain: `keep` moves the note, rewrites the links that name it outside the user's own pages, and writes `moved_from`, the old key; a note it can't move, such as one another program holds open, stays as it was with every link. The rule says what it said, so the note keeps its `updated` and the day it was saved, and the pages that link it don't go stale. A move needs the domain to exist, so a domain offer is kept before the moves into it. Both are offers in every mode, and `keep` logs them in `log.md`.
- **Packages.** A knowledge rule's `package`, `ecosystem/name`, names the library it is about, and `propose` fills `checked_with` from the project's lockfile (see `reference/notes.md`). Once `pages.entityAfterRules` live rules name one package (3 by default, in `vault.config.json`) and no entity page does, the reply says so, and the agent holds an offer of the entity page to release with the others.
- **Held offers.** `propose` with `hold: true` stores the offer as held and shows nothing, so knowledge rules and page changes found during a task reach the user together at its end. `propose` with `release: true` alone returns every offer the session holds. It reads each rule's mode as it runs: where the mode writes at once, outside the vault folder, it writes those rules then; it returns page changes, and the rest, as offers, after what it wrote, with a line before the offers telling a prompting client to call `keep` for each. Under `off`, outside the vault folder, a held rule the user never asked for is not offered, and release says so for it. A rule that fails to write gets a `Not written` line, and the others go on. Two held offers of evidence for one rule both stay unless the evidence is the same; any other held change with the same key replaces the one before, and the reply names it. A release after the sweep queued what the session held names those entries. `keep` refuses a held offer, and the vault-call hook denies its call before recording it, so the offer keeps its one `keep` for after release. A session start after compaction or `/clear` reminds the agent of the offers it still holds.
- **Review queue.** Each session start, waiting at most 2 s in all for another session's sweep or `keep` to finish and otherwise leaving it to the next start, sweeps the offers of other sessions quiet for `queue.sweepAfterHours` (12 by default, in `vault.config.json`; a value that isn't a number above 0 counts as the default, and lint reports it) into `raw/queue/` (see Queue rows in `reference/notes.md`), reading only `.state/offers/` and the session registry; a session whose registry it can't read counts as live. A held offer goes as `unreleased`; a pending one as `skipped` when the user typed after it was shown, which the prompt hook records as `last_prompt` for a message the user typed, not for a task notification or another session's message, otherwise as `ignored`. A pending offer whose `keep` call was recorded and never allowed was denied: the prompt hook marks it `denied` on the user's next message, the sweep marks any it missed, and neither queues it. The call's record stays while its offer is pending, and if the user then allows that very call, `keep` keeps the offer. A subagent's `propose` goes straight to the queue, since its caller can't answer a prompt, and it can't release the session's held offers or offer an entry again. An offer made again from an entry and left unanswered stays that entry. `keep` refuses a queued offer and names the entry, which `propose` with `queued` offers again, a domain entry included.
